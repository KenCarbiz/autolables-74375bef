# SOURCE_TO_FACT_MATRIX — Gate 1, Agent 1 (Vehicle Truth / Data Architecture)

Repo `KenCarbiz/autolables-74375bef` at `83baf7cc`. Live data read 2026-09-09 (UTC) from Supabase project `onnbmmdbrsgytfozfozn` via read-only SELECT. Pilot tenant Harte Infiniti. All file references are repo-relative `file:line`. Every count below is from a query listed in the Evidence index unless marked "Gate 0 report".

## Executive summary

1. The truth engine (`src/lib/vehicleTruth/*`, mirrored under `supabase/functions/_shared/factorySticker/lib/vehicleTruth/*`, differing only by a generated header and two import paths) is a **derived ledger**, not a source of record: its only producer, `candidatesFromListing` (`ingest.ts:116-219`), reads `vehicle_listings` columns and `mc_attributes` after every provider has already written them without precedence.
2. `vehicle_facts` holds 5,042 rows over exactly 20 fact keys and 3 source kinds (marketcheck 2,838 / neovin 1,491 / dealer_confirmed 713). Every fact key has exactly one source kind in the database, so no fact has ever had two candidates; `vehicle_fact_conflicts` is 0 by construction, not by agreement.
3. Facts refresh only when `factory-sticker-orchestrate` runs for that vehicle (`index.ts:574`), and the nightly `orchestrate_sweep` never re-runs a record whose status is in `SWEEP_NEVER_RERUN_STATUSES` = PUBLISHED, APPROVED, SUPERSEDED, ARCHIVED, FAILED_PERMANENT (`index.ts:77-79`, exclusion at `:1489`); `refresh_truth_sweep` defaults to `only_missing` (`:1390`, filters on `vehicle_snapshots` existence `:1396-1402`), and `ingest-orchestrate`'s reconcile re-dispatches a sticker only when no record exists or its status is in `STICKER_RETRYABLE` = PENDING_DATA, FAILED_RETRYABLE, READY_TO_GENERATE (`ingest-orchestrate/index.ts:68, 320-330`). No migration-defined job refreshes facts for a vehicle whose sticker is PUBLISHED. Result on the pilot tenant's 130 published listings (131 across all tenants; the 131st is the other-tenant row in Unknowns item 10): 105 of 117 `advertised_price` facts and 71 of 83 `mileage` facts are older than 7 days; **99 of 117 `advertised_price` facts disagree with `vehicle_listings.price`** (118 facts / 99 disagreeing across all tenants), and of the 99 only 23 are the fee-basis difference; 76 are genuine feed reprices since the last orchestration (§2.4, Q21).
4. There is **no freshness policy in the engine**: `resolveFact` uses recency only as a third tiebreak (`precedence.ts:282`), and `observed_at` is stamped with the orchestration time, not the provider retrieval time (`truth.ts:163`, `ingest.ts:152,166`; `mc_attributes` carries no `retrieved_at`/`specs_retrieved_at` key on any of the 131 published listings (all tenants), and `build_sheet` no `retrieved_at`; `mc_attributes.specs_decoded_at` exists on 110/131 but `ingest.ts` never reads it, Q14). Field-specific freshness exists only outside the engine, as per-column `*_checked_at` stamps and sweep cut-offs (30 d recall, 30 d EPA, 24 h incentives, 7 d crawl backoff).
5. **Stock number cannot be resolved today**: `vehicle_listings` has no `stock_number` column, `mc_attributes.stock_no` is present on 0 of 130 pilot published listings (0 of 131 across all tenants), so the `stock_number` fact is produced for 0 vehicles. The current value lives only on `vehicle_files.stock_number` (130/130 pilot; the other-tenant row has no `vehicle_files` row at all) and `mc_raw.stock_no` (128/130 pilot). One served Passport route does print a "Stock #": `/v/:slug/documents` renders the last six characters of the VIN under that label (`src/pages/VehiclePassportDocuments.tsx:715`; §5 row 6).
6. Five of the twelve critical fields (VIN, stock, MSRP-as-shown, engine, drivetrain) are served to the Passport from columns the resolver either does not read (`mc_attributes.msrp`, `vehicle_files.stock_number`) or reads from a weaker source than the one on file (engine/drivetrain: `marketcheck-specs` does write `mc_attributes.engine/drivetrain` from the NeoVIN build (`marketcheck-specs/index.ts:281,285`), but the nightly sync rebuilds `mc_attributes` from the feed `build` object (`marketcheck-sync/index.ts:1137-1138`) and `DECODE_OWNED_KEYS` (`:95-99`) does not carry those keys forward, so the steady-state value is the feed's; the resolver reads that column as marketcheck HIGH (`ingest.ts:153-155`) and never reads the sheet).
7. `candidatesFromDealerEdits` (`ingest.ts:228-244`) has no production caller (referenced only by `src/lib/vehicleTruth/ingest.test.ts:4,128,140`); `vehicle_facts.overridden_by` is null on 5,042/5,042; `source_authority_rules` has 0 rows; `usable_in_copy` is true on 5,042/5,042. The manual-override path in the engine has never executed.
8. History/title facts (one-owner, clean title, CPO) are resolved at read time by `resolveHistoryFacts` (`historyFacts.ts:30-46`, called from `src/components/listing/TrustStrip.tsx:63`) from `mc_attributes` provenance tags; they are **never persisted** to `vehicle_facts`. Recall, EPA, market, Get Ready, inspections, warranty, incentives and documents likewise never become facts.
9. A second, incompatible fact vocabulary exists: `description_fact_snapshots.facts_json` (492 rows) built by `_shared/description-core.ts:200-410` with sources `inventory_record | marketcheck_feed | vin_decode | vin_decode+feed | nhtsa/marketcheck | vehicle_history_report | cpo_program_source | oem_warranty | tenant_settings` and statuses `verified | feed_provided`, none of which map to the engine's `SourceKind`.
10. Thirty-one direct write paths bypass precedence (section 7). One client write targets a column that does not exist (`TitleVerificationPanel.tsx:124,135` writes `vehicle_listings.title_verification`; the column is absent, so NMVTIS attestations cannot save; the reader `ComplianceTab.tsx:233` passes `vehicle.title_verification`, which is always undefined). Two automatic writers of customer-facing claims were missing from the first draft and are now in §3.3 and §3.9: `sweep_getready_install_safety_net` (nightly 04:30, flips unproven installed lines to optional) and `autopublish_k208_on_signoff` (publishes/reverts the K-208 on inspection sign-off). The prep sign-off gate described in CLAUDE.md is not enforced by the live `enforce_prep_gate` (§3.8).

Tenant rules can re-order or set `warn | block_generation | ignore` (`tenantAuthority.ts:123-140`), but `source_authority_rules` has 0 rows (Q4).

## 3. Matrix by fact family

Scope note: parenthesised counts in §3 are all-tenant figures over the 131 published listings unless labelled pilot; the single other-tenant row's contribution to each is itemised in §2.3, so the pilot figure is the all-tenant figure minus that row where §2.3 shows it present.
