# AutoLabels production RooftopOS packets: apply order

PROPOSAL, NOT APPROVED. Nothing here has been run against production. Every packet is one `DO` statement wrapped in
a sha256-checked outer `DO` (the same wrapper as the staging cards). Each one refuses to run unless the server address is
`2a05:d018:135e:166d:40ff:d4ff:1780:16c1`, session_user and current_user are `postgres` and the server is PostgreSQL 17,
then checks its pre-state, applies, and checks its post-state. Any failure raises and nothing is applied.

Generated by `scripts/rtgip3/gen_prod_al.py` (`--check` proves freshness). Proven locally by
`supabase/tests/rtgip/al-production-packets-test.sh` (PostgreSQL 16, C and ICU en-US databases; 23 checks each).
`SHA256SUMS` is `sha256sum -c` compatible and lists every file; `SHA256SUMS.inner` lists each wrapped file's inner text
(the digest its own wrapper checks).

The result is AutoLabels production installed dark: `transport_enabled = false` under the CHECK lock, `local_app =
'autolabels'`, no connections, no keys, no rtgip/2 key import, the S3 RPCs closed to signed-in users, and the
`rtgip_edge` login for the edge runtime.

## Step 10: what the rtgip_edge login can reach (M-1)

`rtgip_edge` is a direct SQL login. Like every role it holds PUBLIC's USAGE on schema `public` and PUBLIC's EXECUTE on
any function never revoked from PUBLIC, and it can set `request.jwt.claims` itself. So for any SECURITY DEFINER
function in `public` that PUBLIC may execute and that authorizes with `auth.uid()`, `auth.role()`, `auth.jwt()` or the
claims, a holder of `RTGIP_EDGE_DB_URL` can call it as any user or as `service_role`. A PostgREST caller cannot.
The local test reproduces this with a probe function and shows a per-function `REVOKE EXECUTE ... FROM PUBLIC` closes it.

This is strictly narrower than what it replaces: staging ran the runtime with `SUPABASE_DB_URL`, the `postgres` owner
login, which can do all of that and everything else. `rtgip_edge` has no table privilege outside its listed reads, no
write, no inheritance, no BYPASSRLS, and no own grant on any `public` function (fingerprint `edge_no_own_public_grant_ok`).

Before step 10, run `10-EDGE.preread.readonly.sql` and put its output on the step 10 card. It lists (a) the
PUBLIC-executable SECURITY DEFINER functions in `public` whose body reads the claims, and (b) every other
PUBLIC-executable SECURITY DEFINER function in `public` (one may read the claims through a helper). The owner accepts
or revokes per function on that card. Revoking PUBLIC EXECUTE does not change app behavior for functions the API roles
hold explicit grants on, but each one is checked first. Nothing is mass-revoked. Step 10 prints the same inventory as a
NOTICE, and the fingerprint repeats the counts (`edge_jwt_definers`, `edge_jwt_definer_list`, `public_definers`).

Step 10 also takes ACCESS EXCLUSIVE briefly on `public.tenant_members` and `public.dealer_stores` for `CREATE POLICY`
(review L-2). Run it at low traffic; under its 5 s `lock_timeout` it fails atomically rather than queueing longer.

## Rollback rules

- 10, 09, 08, 07 have exact inverses. Run them in reverse order (10, 09, 08, 07). 10's inverse refuses while
  `rtgip_edge` has open sessions; delete the `RTGIP_EDGE_DB_URL` secret first.
- 02b has an exact inverse.
- 01 to 05 create schemas, tables, functions and roles. Removing them is IRREVERSIBLE without point-in-time recovery.
  Their forward recovery is the `.disable.sql` packet (revokes the component's grants; no table, row or audit
  record is dropped), run 05 to 01. `.restore.sql` re-runs the same embedded file to put the grants back: invert
  10 to 07 first, restore 01 to 05 in order, run 02b, then re-apply 07 to 10. A restore over a later step still applied
  refuses atomically on its digest check (proven locally).
- 06 is IRREVERSIBLE by design: it only revokes `sandbox_exec` write privileges, which are never wanted back.

## Deployment steps (each needs its own owner approval)

1. Merge (the owner's merge approval is the edge deploy approval). Pushing `main` auto-publishes, and Lovable's sync
   deploys the three edge functions `rtgip-inbound`, `rtgip-dispatch` and `rtgip-publish` immediately, before any
   database step. That is safe: with no `RTGIP2_RUNTIME_MODE` they answer 503 `runtime_mode_off` before reading a body,
   a secret or a row (config.toml: inbound and dispatch `verify_jwt = false`, publish `true`).
2. Take a backup or confirm PITR is on for project `onnbmmdbrsgytfozfozn`.
3. Run the read-only fingerprint once before step 01 and keep the output (expect every component absent).
4. Apply 01, 02, 02b, 03, 04, 05, 06 in one sitting, then 07, 08, 09, through the SQL editor as `postgres`, one file
   per run. Keep each NOTICE (`*_ok`).
5. Run `10-EDGE.preread.readonly.sql`; owner card decides per function (M-1).
6. Separate card: step S10 on AutoLabels Staging (M-4).
7. Apply step 10. Keep its inventory NOTICE.
8. Set the `rtgip_edge` password as a SCRAM verifier (no plaintext in SQL, e.g. psql `\password rtgip_edge`), then set
   the edge secret `RTGIP_EDGE_DB_URL` (pooler user `rtgip_edge.onnbmmdbrsgytfozfozn`; the runtime forces TLS with
   `ssl: "require"` and refuses a URL with `sslmode=disable`, `allow` or `prefer`).
9. Run the fingerprint; every `*_ok` column must be true.
10. Later card (P4), rebuild and second push: rebuild the bundle with `RTGIP_PRODUCTION_GATEWAY_ORIGIN` set to the
    production Gateway origin (`node scripts/rtgip2/build-runtime.mjs`; it refuses any esbuild other than the pinned
    0.25.12). That changes the bundle sha256. Commit and push it to `main`; this is a second auto-publish. Set
    `RTGIP3_VERIFIER_DIGEST` to the NEW sha256 from `rtgip2-runtime.bundle.js.sha256`. Never set it to the digest of
    the committed placeholder build (`20f904ad...`), which can never dispatch.
11. Enrollment (later cards, P4): T1 connections for the tenant and rooftop, the owner key ceremony, T2 K5-v3
    bindings, `RTGIP2_RUNTIME_MODE=production`, then the transport and flag cards. None of these is part of the dark
    install.

## Build inputs (review L-5)

- esbuild is pinned exactly: `build-runtime.mjs` refuses any version other than `PROVENANCE.json`
  `bundle.esbuild.autolabels` (0.25.12).
- The bundle imports `npm:postgres@3.4.5`, the exact driver the staging AutoLabels runtime ran (bdbe070a bundle).
  `package.json` `postgres ^3.4.9` is only the copy tsc and vitest resolve; it is not deployed.
- TLS: `ssl: "require"` encrypts without verifying the certificate chain. Supabase database and pooler certificates
  chain to the Supabase root CA, which is not in Deno's trust store, so `verify-full` would refuse every connection
  until that CA is shipped as `ssl: { ca }` (open item).
